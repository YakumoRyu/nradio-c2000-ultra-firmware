## 2026-10-23 媒体保护与Emby恢复

Emby正常退出、OOM标记为false，保护状态确认因低内存主动停服。旧恢复门槛要求CPU低于50%，Docker查询超时还会使整轮资源采样中断。保护程序改用有超时的Docker本地HTTP接口，并在失败时用经过Docker cgroup校验的进程信息继续监测；保护目标在停止前保存，按依赖顺序逐个恢复，并将所有权持久保存以跨重启继续处理。

Emby的memory.high采用320MiB，保留384MiB硬限制；192MiB试验值曾造成大量程序页重读，已撤回。全局VM参数恢复原值。本次保留后台追赶分析、两个并发限制均为1。资源指标写tmpfs，TF卡只在保护目标/动作变化时保存状态。Docker超时或TF状态保存失败均不能中断路由资源保护。

13项针对性测试通过，媒体库及内外网视频分段读取通过。最终180秒监测CPU42.24%–74.04%，后台响应中位6毫秒、Emby13毫秒、MediaWarp14毫秒，Emby高水位事件没有增加，保护采样保持更新。用户在排查期间手动重启，并确认重启后均正常；这次整机卡死的唯一触发原因未在现存日志中得到证明。

双包：ultra-maintenance-20261023-2、完整预发布ultra-25.12-20261023-r9。r9只更新两个媒体文件及两个版本/仓库标识，内核和无线模块与r8相同。完整镜像与在线补丁分别验收。

## 2026-10-23 Emby再次停止与r10修复

第二次故障时Emby已退出、OOMKilled=false，而保护状态的stopped_by_guard为空、last_action仍是stop_media/requested。r9的恢复分支将Running=true直接当作恢复完成；Docker停止请求超时后容器仍短暂运行，导致所有权过早丢失。新增延迟退出完整循环测试在r9代码失败，在修正版通过。

r10为每个保护目标保存stopping、stopped、starting阶段。停止中的Running=true保留目标；只有Docker明确报告已停止才进入可恢复阶段，只有已发出启动请求且确认运行才释放目标。查询失败且未找到进程是unknown，不能作为停止确认。阶段和触发压力样本持久保存，同一待停目标不重复请求停止。升级时仅迁移旧版停止记录中已被Docker确认退出的目标，不接管其他手工停止服务。21项测试通过，实机以恢复队列启动Emby，未手工启动容器或重启网络。
